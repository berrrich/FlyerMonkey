# Mission 012B — mobile customer authentication

## Scope and inspection

Android uses `FlyerMonkey/FlyerMonkey/MauiProgram.cs` (the root `FlyerMonkey/MauiProgram.cs` is not the mobile project startup). Products/offers and approved artwork use the published read-only HTTPS API. Previously the non-Web ProductDetail branch offered `ImageGenerationApiService` at `api/images/generate` and the legacy saved-artwork gallery. These are local/operator-era interfaces, not the CustomerBearer flow. Android Debug selected HTTP localhost:5145, requiring `adb reverse tcp:5145 tcp:5145`. The generic failure message combined authentication, permission, transport and server failures.

The mobile customer branch now replaces those controls and suppresses their history loading. It has no generation button and makes no generation, preview, provisioning or credit requests. Website rendering and operator authentication remain separate. Other MAUI platforms retain their prior behavior; this implementation targets Android.

Shared: tenant/API identity constants, `CustomerAccount`, product routing and Razor presentation. Platform-specific: MSAL public client, system browser, Android callback, encrypted cache and lifecycle. Website confidential-client credentials, cookies, antiforgery and server token acquisition are never used by mobile. The API still maps validated tenant/object claims through the existing repository; mobile never sends CustomerId or email to choose an account.

`GET /api/customers/me` is the API endpoint behind the website's `/customer/me`. Its existing Mission 011A response deliberately masks CraterEnabled=false. Mobile accurately presents that server response as unavailable; it must not infer actual SQL eligibility. This mission does not call the separately gated customer attempt endpoint or enable generation. Existing customers sign in on mobile without provisioning. A missing account directs the customer to existing website setup; no automatic mobile account creation or email matching occurs.

## Android transport and tokens

Default customer API is `https://localhost:7255/`; catalogue browsing continues using its existing published API. Use `adb reverse tcp:7255 tcp:7255` to reach the host's loopback HTTPS listener from Android. Device localhost alone refers to the emulator. `10.0.2.2` is the emulator host alias, but does not match a localhost certificate and conflicts with customer Crater's loopback boundary. Do not switch bearer traffic to HTTP or install an accept-all certificate callback.

The emulator must trust the host development HTTPS certificate through the approved Android Debug trust setup below. Windows `dotnet dev-certs https --trust` alone does not configure Android trust. Do not commit certificates/private keys or broaden Release trust. The API must be running with existing customer authentication enabled and all generation gates disabled. Initially, emulator-5554 had no reverse mapping and neither API port was listening; the approved follow-up now provides the HTTPS listener and port 7255 mapping.

Customer tokens are kept in a dedicated MSAL public client using MSAL's Android secure persistent cache. The November 3 correction removes unsupported custom MAUI SecureStorage serialization callbacks; the earlier implementation could fail on first client initialization. Backups are already disabled. Tokens and customer identifiers are not logged, placed in URLs, displayed in the UI, or passed to WebView JavaScript. Silent acquisition restores the cached account and refreshes expired access tokens; UI-required responses return to explicit sign-in. Multiple cached accounts require explicit account selection. API reads never open a browser automatically. The current product page remains mounted during interactive sign-in, preserving the product and Crater context; process termination during browser sign-in requires reopening the product.

Sign-out removes customer accounts and secure cache only. It does not remove operator accounts or clear the shared browser/Google/Facebook session. Future explicit sign-in uses the account picker. Profile refresh clears previous eligibility before requesting current server state. Transport/certificate errors, timeouts, 401, 403, 404, other HTTP errors and invalid JSON have distinct customer messages. No HTTP retry handler is installed. No generation is retried or dispatched.
